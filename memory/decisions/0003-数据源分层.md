# ADR-0003：数据源从「单源 AKShare」改为「分层多源」

- 日期：2026-09-01
- 状态：已采纳（代码实施待排期）
- 关联：ADR-0002 不废除，但 AKShare 从「唯一数据源」降级为「L3 补缺源」

## 零、结论修正（2026-09-01，本 ADR 的最终立场）

写完 §一~§九 之后，重新问了一个更基本的问题：**既然是数量问题，为什么不直接限量？**

这个问题是对的，它把本 ADR 的优先级整个翻过来了：

> **限量是主方案，换源是 Plan B。**

理由：一次正常复盘只需要 30–50 个请求。这个量级下，东财、新浪从来不封人——
8-31 被封是因为重试风暴把它放大到了几百个。也就是说，
**问题不在"用了免费源"，而在"没有人给请求量设过上限"。**
在没设上限之前就去换源，等于把同一个 bug 搬到新源上重演一遍。

于是先做了 `scripts/ak_client.py` 的**每日请求预算**（见 §十），
它和已有的限流、熔断构成三道闸：

| 闸 | 管什么 | 触发时机 |
|---|---|---|
| 限流 `MIN_INTERVAL` | 请求之间太密 | 每个请求前 |
| **预算 `MAX_REQUESTS`** | **每个都成功、但总量失控** | **每个请求前** |
| 熔断 `circuit.json` | 已经开始被拒 | 连续失败之后 |

中间那道是新加的，也是唯一能在**出事之前**看见问题的。
熔断只能在被拒之后止损，预算能在还全是 200 的时候就叫停。

**因此 §四的三层结构降级为"以后要做的事"，不是现在要做的事。**
现在的做法是：继续用 AKShare，把请求量摁在 30–50 个/天。
只有当"预算内也取不到"持续发生时，才启动 §四的换源。

## 一、触发事件

ADR-0002 写过三个「何时该重新考虑」，第三条已命中：**出现持续性限流导致每日复盘跑不完**。

2026-08-31 起 eastmoney 对本机 IP 持续拒绝：DNS 正常、TCP 通、TLS 握手完成、请求发出，
服务端静默关闭连接（curl 退出码 52 Empty reply from server），七种请求方式（urllib / requests /
trust_env=False / identity 编码 / Connection: close / 裸 socket+TLS / curl）表现完全一致
——这排除了 shell、Python、代理、证书，指向 **IP 级封禁**。legulegu 同样不可达，新浪始终可用。
完整诊断与「重试是负债不是资产」的教训见 `memory/knowledge/akshare-gotchas.md`。

## 二、先纠正一个因果判断

> 「AKShare 不稳定，所以我们必须挂 VPN」

因果反了。

- AKShare 的 A 股数据全部来自**境内网页接口**（东财 push2/push2his、新浪、legulegu）。
  挂 VPN 后出口 IP 在境外，这些接口**更容易**拒绝你，不是更容易通。
- 真正需要走代理的是 **LLM API**（Anthropic / OpenAI / OpenRouter），不是数据。

所以正确做法是**按流量分流**，而不是换库：

| 流量 | 路径 |
|---|---|
| LLM API 调用 | 走代理 / VPN |
| 行情数据抓取 | 直连，绕过代理 |

代码里已有能力（`ASTOCK_DIRECT=1`、`trust_env=False`、把 DATA_HOSTS 写进 `no_proxy`），
但此前是「出问题时的应急开关」。**本 ADR 把它定为默认策略**：数据层永远直连，LLM 层读代理配置。

## 三、候选评估

九章复盘里，被封时真正断掉的是三块数据。以它们为标尺评估候选：

| 数据源 | 接入方式 | 涨停池/连板/炸板率 | 板块行情与资金流 | 涨跌家数 | 免费 | 网络路径是否独立于东财 |
|---|---|---|---|---|---|---|
| **Tushare Pro** | token，单一 host `api.tushare.pro`，POST JSON | ✅ `limit_list_d`（含 `limit_times` 连板数、`limit=D/U/Z` 跌停/涨停/炸板） | ✅ `moneyflow_ind_dc`（东财口径板块资金流）、`ths_daily`（同花顺板块行情，无成交额） | ✅ 用 `daily(trade_date=)` 全市场快照自己算 | ❌ 需积分 | ✅ 完全独立，且代理/直连都能走 |
| **BaoStock** | 免费、无 token、自有 TCP 协议（:10015） | ❌ | ❌ | ✅ 可由全市场日线算 | ✅ | ✅ 非 HTTP，路径完全独立 |
| **mootdx / pytdx** | 通达信行情服务器，TCP 二进制协议 | ❌（无东财口径涨停池） | 部分（通达信板块，口径不同） | ✅ 全市场快照 | ✅ | ✅ |
| **adata / efinance** | Python 库 | ✅ | ✅ | ✅ | ✅ | ❌ **底层仍是东财/腾讯/百度同一批 host** |
| **麦蕊智数 mairui** | 商业 token HTTP API | ✅ | ✅ | ✅ | ❌ 低价付费 | ✅ | 
| **交易所官方（上交所/深交所/中证）** | 官网接口 | ❌ | ❌ | ✅ 市场总貌，口径最权威 | ✅ | ✅ | 
| 聚宽 / 米筐 / 掘金 | 研究平台 SDK + 授权 | ✅ | ✅ | ✅ | 有限免费 | ✅ | 
| Wind / Choice | 商业终端 | ✅ | ✅ | ✅ | ❌ 昂贵 | ✅ | 

**关键结论**：
1. `adata` / `efinance` 这类「多源融合 + 动态代理」的库，**换库不换命**——底层还是同一批被封的 host。
2. 只有 **token 型 API**（Tushare / 麦蕊）和 **非 HTTP 协议**（BaoStock / 通达信）真正换了网络路径。
3. 免费且覆盖涨停池的，**不存在**。这是 ADR-0002 当初选 AKShare 的原因，今天依然成立——
   只是「免费」的代价从「偶尔重试」涨到了「会被封 IP」。

## 四、决定：三层结构

```
L1  Tushare Pro    主源。token 单 host，最稳，需要积分
L2  BaoStock       兜底。免费、独立协议，只覆盖行情骨架
L3  AKShare        补缺。只用来取 L1/L2 都没有的东西，且必须限流 + 熔断
```

按 dataset block 分配：

| 数据块 | 主源 | 兜底 |
|---|---|---|
| 交易日历 calendar | BaoStock | Tushare `trade_cal` |
| 指数日线 index_daily | Tushare `index_daily` | BaoStock / 新浪（已实现） |
| 指数分时 intraday | AKShare（东财） | 无 → `missing` |
| 个股行情 stocks | Tushare `daily` + `daily_basic` | BaoStock |
| 涨跌家数 breadth | 由 Tushare `daily` 全市场快照计算 | 交易所总貌 |
| 涨停/炸板/连板 limit_pool | Tushare `limit_list_d`（5000 分） | AKShare `stock_zt_pool_*` |
| 板块行情 sectors | Tushare `ths_daily`（成交额缺，需标注） | AKShare |
| 板块资金流 sector_flow | Tushare `moneyflow_ind_dc`（6000 分） | AKShare |
| 北向 northbound | Tushare `moneyflow_hsgt` | 可缺 |
| 新闻公告 news | AKShare / 交易所 | 可缺 |

## 五、积分门槛与降级路径（学生必须知道）

Tushare 积分是硬门槛，且短线数据在高档位：

| 积分 | 能力 |
|---|---|
| 120（注册即得） | 只有基础不复权日线，**不够用** |
| 2000 | 标准接口，200 次/分钟 —— 指数、个股、日历、涨跌家数够了 |
| 5000 | `limit_list_d` 涨停/跌停/炸板 |
| 6000 | `moneyflow_ind_dc` 板块资金流 |

**如果学生不付费**：第 ③ 章（板块与题材）与情绪面的涨停梯队会拿不到数据。
此时按既定硬规则处理——标 `blocked` + 在报告顶部声明缺失，**不允许用别的口径凑数**，
其余八章照常产出。这正是「文件契约 + blocked 状态」设计的价值：缺一块不会毁掉整份复盘。

## 六、明确不做的事

- **不引入 adata / efinance 做「自动多源切换」**：底层同 host，等于把同一个封禁包装了一层。
- **不用新浪 `stock_zh_a_spot` 兜底涨跌家数**：AKShare 文档自己写了「重复运行本函数会被新浪暂时封 IP」，
  新浪是眼下唯一还活着的源，不能在它身上重犯 8-31 的错误。
- **不上 Wind / Choice / 聚宽 / 米筐**：授权与门槛不适合教学项目。

## 七、口径风险（跨源必须记账）

Tushare 的涨停判定与东财涨停池口径不同（ST、新股、一字板、B 股的处理不一致），
同花顺板块与东财板块的成分股也不同。因此：

1. 每个 DataBlock 的 `provenance.source` 必须记录**实际命中的源**，不能写「多源」。
2. 同一指标在一次复盘内**不允许混源**（今天用 Tushare 明天用东财会让环比失真）。
3. 换源当天要在 `memory/knowledge/` 记一条口径差异，报告里跨日对比需标注。

2. `scripts/providers/`：`tushare.py` / `baostock.py` / `akshare.py` 三个 provider，统一返回 `DataBlock`

## 九、零成本路径（本项目采用）

约束：**不为数据花钱**。以下是这个约束下能拿到什么、拿不到什么、以及怎么才不会再被封。

### 9.1 先看清「免费」的边界

| 数据 | 免费能不能拿到 |
|---|---|
| 交易日历、四大指数日线、个股日线与复权、涨跌家数、成交额 | ✅ 完全可以，且有多个独立来源 |
| 指数分时（四段） | ⚠️ 只有东财/通达信，可拿但不稳 |
| 板块行情（涨跌幅、成交额） | ⚠️ 通达信板块可拿，但口径 ≠ 东财/同花顺 |
| **涨停梯队 / 连板数** | ⚠️ **有免费独立备胎**——同花顺涨停揭秘（`data.10jqka.com.cn`，独立风控面）。见 ADR-0004 §3.4 |
| **炸板率 / 跌停池** | ❌ 免费只有东财（炸板池的分子别处没有） |
| **板块主力资金流** | ❌ 同上 |

Tushare 有**在校学生/教师免费积分**（提交学生证或学信网截图，走高校服务通道）。
但它开放的是「基础信息 + 日线行情 + 财报」档位，**够不到** `limit_list_d`（5000 分）
与 `moneyflow_ind_dc`（6000 分）。也就是说：**学生认证解决第 ①②④⑤ 章，解决不了第 ③ 章的涨停梯队与资金流。**

结论：**九章里有八章可以完全免费且稳定地跑起来；第 ③ 章的板块资金流与炸板率在免费世界里没有稳定来源。**

> **2026-09-01 修正**：原本这里写的是「涨停池免费只有东财」。读了 a-stock-data 之后
> 发现同花顺有一条独立域名的涨停揭秘接口，能覆盖涨停家数、连板梯队和题材归因，
> 覆盖不到的只是炸板池与跌停池。详见 ADR-0004 §3.4。

### 9.2 真正的杠杆不是换源，是请求量

8-31 被封不是因为用了免费源，是因为**重试风暴**：一次失败触发多次回退，回退又失败，
把请求量放大了一个数量级。免费栈能不能活下来，取决于每天发多少个请求。

零成本方案的核心因此是三条**约束**，而不是三个新库：

1. **历史只取一次** —— 日线/指数历史落地本地（SQLite 或 parquet），之后只取增量。
   一次复盘的请求量从「几百」降到「几十」。
2. **每日请求预算** —— `ASTOCK_MAX_REQUESTS` 硬上限，超了直接 `blocked`，**不重试**。
   把「重试是负债不是资产」写成机制。
3. **熔断常开** —— 已实现（`circuit.json`，3 次失败冷却 10 分钟，冷却期发 0 个请求）。

### 9.3 零成本栈

```
L1  BaoStock            免费无 token，自有 TCP 协议 :10015
                        → 交易日历、指数日线、个股日线（含复权）、涨跌家数（全市场快照自算）
L2  Tushare（学生认证）  免费积分档位，与 L1 同类数据互为对照与兜底
L3  mootdx / pytdx      通达信行情服务器，二进制协议
                        → 实时快照、分时、通达信口径板块行情
L4  AKShare（东财）      **只保留两个调用**：涨停池、板块资金流。
                        每天各 1 次，限流 + 熔断 + 缓存，失败即 blocked，绝不重试
L5  交易所官网           上交所/深交所市场总貌，作为涨跌家数与成交额的权威校验
```

四个源，但**每个数据块仍然单源**（遵守 §7：一次复盘内不允许同一指标混源）。

### 9.4 明确不进默认路径的免费源

- **pywencai（同花顺问财）** —— 能查涨停/连板，但需要 Node.js v16+ 执行 JS、需要手动从浏览器抄
  cookie，且作者自己写明「反对高频调用，高频会被问财屏蔽」。
  让学生装 Node 再抄 cookie，违背「pip install 完就能跑」的教学目标。
  → 列为**你个人可选**的补充，不写进默认 pipeline。
- **adata / efinance** —— 底层同一批 host，换库不换命（见 §3）。

### 9.5 承认代价

零成本不是零成本，成本从钱转移到了三处：

1. **你要维护 4 个 provider 的口径差异**（通达信板块 ≠ 东财板块）
2. **第 ③ 章会经常缺** —— 东财一封就没有替代
3. **偶尔的缺章要靠机制兜住**，而不是靠临时补数据

第 2 条对教学项目反而是好事：`blocked` 状态、报告顶部的缺失声明、契约设计让缺一块不毁整份——
这些平时讲不清楚的东西，缺数据的那天学生一次就懂了。**绝不允许**为了让报告好看而换口径凑数。

## 十、每日请求预算（已实现）

`scripts/ak_client.py`：

```python
BUDGET_FILE  = CACHE_DIR / "budget.json"
MAX_REQUESTS = 300   # 全部域名合计 / 天   ← ASTOCK_MAX_REQUESTS
MAX_PER_HOST = 120   # 单域名 / 天         ← ASTOCK_MAX_PER_HOST
class BudgetExceeded(FetchError): ...
```

四个设计点，每一个都是从 8-31 那次学到的：

1. **检查在最底层** —— 放在被 patch 的 `Session.request` 里，
   走 akshare 哪个接口、走主源还是备用源、走不走代理，一律绕不过。
2. **超额在请求发出之前抛错** —— 测试 `test_budget_stops_before_the_request_is_sent`
   断言的就是这一点：撞上限那一刻，第 N+1 个请求**一个字节都没出去**。
3. **落盘按日计数** —— 用户会反复重跑脚本。只存内存的上限，重启一次就归零，等于没有。
   跨日自动清零，不需要人管。
4. **`BudgetExceeded` 继承 `FetchError`** —— `call()` 里 `except FetchError: raise`，
   所以它直接冒泡，**不会被重试逻辑当成网络错误再打三次**。
   否则"限量"就变成了"限量之后再打三次"，正好是它要防的事。

另外：**命中缓存的调用根本走不到 `Session.request`，天然不计数**——
这条让"把缓存做厚"成为真的省额度，而不是自欺欺人（有测试守着）。

用法：

```bash
python tools/astock.py budget            # 今日用量 + 按域名分布
python tools/astock.py budget --reset    # 清零
```

`doctor` 里也加了一行，用到 90% 会报警。

### 预算是上限，不是减量

预算防的是事故，它不会让正常复盘少发请求。减量是另一件事，见 §十一。

## 十一、本地行情仓库（已实现）

`scripts/store/bars.py`，SQLite，主键 `(数据集, 标的, 日期)`。

### 和缓存的区别

这是整件事的关键，也是最容易混淆的地方：

|          | 缓存 `workspace/cache/*.csv` | 仓库 `workspace/history.sqlite` |
|----------|------------------------------|--------------------------------|
| 键       | 请求参数的哈希               | (数据集, 标的, **日期**)        |
| 失效     | TTL 30 分钟                  | **永不**                        |
| 省下的   | 这一次请求                   | **以后所有**对这一天的请求      |
| 适用     | 实时快照、盘中数据           | 日线、分时、交易日历这类历史事实 |

一个**已经收盘的交易日**，它的开高低收成交额永远不会再变。
对这种数据谈"过期"没有意义——它不该有 TTL，它该被存下来。

### 实际省下多少

诚实地说，分场景：

| 场景 | 之前 | 之后 |
|---|---|---|
| 每天第一次复盘 | 30–50 个请求 | **基本不变**（今天的数据本来就没存过） |
| **同一天重跑**（调试、改了持仓再跑、报告没渲染好） | 每次都重打一遍 | **指数日线与分时 0 个请求** |
| `--as-of` 复盘过去某一天 | 每次都重打 | **0 个请求** |
| weekly 模式回看一周 | 重复取 5 天 | **0 个请求** |

8-31 被封发生在**反复重跑**的过程中，不是在"每天跑一次"的稳态里。
所以这个仓库正好打在出事的那个场景上。

另外有一个**能力上的增量**，不只是速度：
东财分时接口只保留最近几个交易日，过了窗口就再也取不到。
存下来之后，"复盘上个月某一天的日内四段"从不可能变成可能。

### 四条守住的规则（每条都有测试）

1. **只存已收盘的交易日**（`is_settled()`，默认 15:05 之后）。
   盘中把还在跳的"收盘价"冻成历史事实，之后再也不会被纠正——比取不到数严重得多。
2. **用交易日历判断缺不缺，不用日期减法。** 否则国庆假期会被永远当成"缺 7 天"，
   每次复盘都去重取，仓库反而变成新的请求放大器。
   实现上是硬约束：**拿不到交易日历就不启用仓库**。
3. **降级源的数据不入库。** 新浪备用源没有成交额，一旦存进去就再也不会回头问东财，
   "某天临时降级"会被永久固化成"那天就是没有成交额"。缺一次可以补，存错了不会自己好。
4. **仓库坏了不能拖垮复盘。** 它是优化不是依赖，读写全部包 try/except，
   失败就退化成"这次全走网络"。

python tools/astock.py store            # 存了哪些数据集、覆盖到哪天
python tools/astock.py store --purge    # 清空（删了会自动重建，只是多花几个请求）
