# 01 · 什么是 agentic workflow

## 一、三个阶段

```
阶段一：Prompt
  人 → [一段话] → 模型 → 文本
  模型只会说，不会做。

阶段二：Tool Use（工具调用）
  人 → 模型 ⇄ [工具] → 结果
  模型能查天气、能跑代码了。但仍然是一问一答，没有过程。

阶段三：Agentic Workflow
  人 → [Agent 系统] → 产物
        ├─ 自己拆解任务
        ├─ 自己决定调哪个工具
        ├─ 自己检查中间结果
        └─ 出错自己重试或如实上报
  模型有了"过程"，而过程需要被工程化管理。
```

**本项目在阶段三。** 而阶段三的工程量，90% 不在写 prompt，在管理这个"过程"。

## 二、Agent 的最小定义

一个 agent 需要四样东西：

1. **目标** —— 我要完成什么（`agents/*.md` 的"职责"节）
2. **上下文** —— 我能看到什么（frontmatter 的 `reads`）
3. **能力** —— 我能做什么（`skills` + `tools`）
4. **终止条件** —— 什么时候算完成（frontmatter 的 `writes` + `schema`）

缺任何一样，agent 都会跑飞：
没目标 → 漫游；没上下文边界 → 乱读；没能力 → 空谈；没终止条件 → 停不下来或半途而废。

## 三、为什么"多"agent

见 README 第一节的四点。这里补一个学生最容易忽略的角度：

**多 agent 的价值不只是分工，更是"制造独立性"。**

本项目让基本面、技术面、情绪面三路**互相看不见**，
是为了让它们的结论在统计意义上尽可能独立。
三个独立来源都指向同一个方向，才叫印证；
一个模型顺序看完三类数据后说"三方共振"，那多半只是它在自我说服。

## 四、Agentic ≠ 全自动

一个常见误解是"agentic 就是让 AI 全权处理"。恰恰相反：

**好的 agent 系统会主动制造"停下来"的时机。**

本项目里有三处刻意的"停"：
- 数据缺失 → `blocked`，不猜
- schema 校验失败 → 重试或失败，不放行
- `TODO(strategy)` → 不许 agent 自己决定策略参数

> 判断一个 agent 系统成不成熟，不看它能自动做多少，
> 看它**知不知道自己什么时候不该做**。
