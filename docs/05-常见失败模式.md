# 05 · 常见失败模式

多智能体系统坏起来，往往**不报错**。这才是最麻烦的。
本篇列出八种典型失败，以及本项目对应的防御设计。

## 1. 静默的接口错位

**症状**：上游改了字段名，下游读到 `None`，然后基于空数据写出一份读起来非常合理的报告。

**防御**：`schemas/` 钉死契约 + `validate_after_each_step: true` 每步强制校验。

## 2. 幻觉填空

**症状**：数据缺失时，模型用训练数据里的"常识"补上——
"A 股涨停家数通常在 60 家左右"，听起来对，但不是今天取回来的数。

**为什么危险**：它给出的数字往往**接近正确**，人工复核时容易放过。

**防御**：
- `forbid_fabricated_data: true`
- 每条结论必须有指向 `dataset.json` 的 `evidence`
- 数据缺失时必须 `blocked`
- `tests/test_breadth.py::test_missing_pool_is_flagged_not_faked` 直接测这条

示例 run 里刻意保留了北向资金缺失，就是这个设计的演示。

## 3. 替持仓找理由

**症状**：板块分析师知道你重仓了某个题材，于是为那个题材找强的理由。

**为什么危险**：这是本系统**最危险**的失败模式。
它会用很专业的语言，把你已有的偏见包装成客观结论——
比没有系统更糟，因为它给了你虚假的信心。

**防御**：`sector-analyst` 的 `reads` 里**没有** `positions.yaml`；
调用顺序是先市场 → 再板块 → 最后持仓，前面的结论不知道后面存在。

## 4. 报告层的过度圆滑

**症状**：市场分析师说弱势、板块分析师说主线强，报告写成
"结构性行情，可择优参与"——一句话把矛盾抹平了。

**为什么危险**：最隐蔽的一种，因为报告看起来质量很高。

**防御**：`report-writer.md` 明确禁止抹平矛盾；
示例报告里"指数红、情绪凉"就是把矛盾直接写在第一句。

## 5. 建议不可执行

**症状**："视情况减仓""关注主线延续性""注意风险控制"。

**为什么危险**：第二天早上 9:30，这些话一句都用不上。
写了等于没写，但会让人产生"我有计划了"的错觉。

**防御**：
- `single_action_per_position: true` —— 每只持仓只能有一个动作
- 章节五的时间轴必须写成 **if-then**
- 章节八的观察信号**不多不少正好三个**（两个不够，四个记不住）
- `tests/test_contracts.py` 检查这三条

## 6. 编排者越权

**症状**：orchestrator 觉得"这步简单，我顺手做了"，自己下了分析结论。

**防御**：`orchestrator.md` 的边界节明确禁止；它的 `writes` 里只有 manifest。

## 7. 上下文膨胀

**症状**：为了让 agent"更聪明"，把所有技能、所有明细数据都塞进上下文，
结果模型注意力被稀释，反而变笨。

**为什么危险**：症状是"模型质量下降"，很容易被误诊为"该换个更强的模型"。

**防御**：
- 技能按需加载（agent frontmatter 的 `skills` 字段）
- `dataset.json` 只放摘要，明细落 CSV 供回查
- `memory/MEMORY.md` 只做索引不放内容
- agent 的 `reads` 写死

## 8. 分析永远是事后诸葛亮

**症状**：每天的报告都能把当天的走势解释得头头是道，
但从来没有人回头检查"昨天的判断对不对"。

**为什么危险**：不做验证，你会越来越擅长**解释过去**，
而不是**预判未来**——而且你不会察觉这个区别。

**防御**：
- `news.json` 的 `verification_log`：每天回验昨天的新闻解读
- `sectors.json` 的 `verify_tomorrow`：验证条件必须**可证伪**，
  次日 10:00 前就能得到答案
- `memory/runs/`：留下每天的结论，供回溯统计

这是本项目里唯一一条**没有代码能保证**的防御——
它依赖你每天真的去看那张验证表。

## 一张自查表

给任何 agent 系统体检，问这八个问题：

- [ ] 上游改字段，下游会**报错**还是**静默变空**？
- [ ] 数据缺失时，产物里能不能看出"这里本来该有东西"？
- [ ] 做判断的 agent 知不知道"我方立场"？（它该不该知道？）
- [ ] 最终产物有没有地方**必须**写"我们内部有分歧"？
- [ ] 给出的建议，第二天早上九点半能不能直接执行？
- [ ] 编排者有没有偷偷干活？
- [ ] 每个 agent 的上下文里有没有它用不到的东西？
- [ ] 昨天的判断，今天有没有人回头检查？

## 练习

1. 在本项目里找出至少三处专门防御"幻觉填空"的设计。
2. 失败模式 3（替持仓找理由）和失败模式 4（过度圆滑）都与"立场"有关，
   它们的区别是什么？
3. 设计一个自动检查：如何用代码检测出
   "report.md 里出现的某个数字没有出现在任何一份上游产物里"？
   （提示：这能挡掉大部分幻觉填空）
