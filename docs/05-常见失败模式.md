# 05 · 常见失败模式

多智能体系统坏起来，往往**不报错**。这才是最麻烦的。
本篇列出七种典型失败，以及本项目里对应的防御设计。

## 1. 静默的接口错位

**症状**：上游改了字段名，下游读到 `None`，然后基于空数据写出一份读起来非常合理的报告。

**为什么危险**：没有异常、没有红字，报告长得跟正常的一模一样。

**防御**：`schemas/` 钉死契约 + `validate_after_each_step: true` 每步强制校验。

## 2. 幻觉填空

**症状**：数据缺失时，模型用训练数据里的"常识"补上——
"贵州茅台的毛利率通常在 91% 左右"，听起来对，但不是这次取回来的数据。

**为什么危险**：它给出的数字往往**接近正确**，人工复核时容易放过。

**防御**：`forbid_fabricated_data: true`；每条结论必须有指向 `dataset.json` 的 `evidence`；
数据缺失时必须 `blocked`。示例 run 里的情绪面就是这个设计的演示。

## 3. 确认偏误的串联

**症状**：agent A 说"利好"，agent B 看到 A 的结论后倾向于也找利好证据，
最后三路"共振"。

**为什么危险**：看起来是最强的信号，实际上是同一个判断被复述了三遍。

**防御**：三路分析 agent 的 `reads` 里**只有 `dataset.json`**，互相看不见彼此的产物。

## 4. 编排者越权

**症状**：orchestrator 觉得"这步简单，我顺手做了"，自己下了分析结论。

**为什么危险**：破坏了分工，也让产物无法追溯到具体 agent。

**防御**：`orchestrator.md` 的边界节明确禁止；它的 `writes` 里只有 manifest。

## 5. 上下文膨胀

**症状**：为了让 agent"更聪明"，把所有 skill、所有历史记忆都塞进上下文，
结果模型注意力被稀释，反而变笨。

**为什么危险**：症状是"模型质量下降"，很容易被误诊为"该换个更强的模型"。

**防御**：skill 按需加载；`memory/MEMORY.md` 只做索引不放内容；
agent 的 `reads` 写死。

## 6. 无限重试与打转

**症状**：某步失败 → 重试 → 又失败 → 换个方式再试 → 消耗大量 token 后仍然失败。

**防御**：`pipeline.yaml` 的 `retry` 上限 + `timeout_seconds`；
`required: false` 的步骤失败就标 `blocked` 继续走，不死磕。

## 7. 报告层的过度圆滑

**症状**：三路结论互相矛盾，report-writer 为了让报告"读起来顺"，
写成"综合来看，公司基本面稳健，短期走势震荡，市场关注度适中"——
一句话把所有分歧抹平了，等于什么都没说。

**为什么危险**：这是最隐蔽的一种，因为报告看起来质量很高。

**防御**：`report.schema.json` 强制要求 `divergences` 数组；
报告模板里「分歧与印证」是不可省略的章节；
`report-writer.md` 明确禁止"为了报告好看而抹平分歧"。

## 一张自查表

给任何 agent 系统体检，问这七个问题：

- [ ] 上游改字段，下游会**报错**还是**静默变空**？
- [ ] 数据缺失时，产物里能不能看出"这里本来该有东西"？
- [ ] 几个 agent 的结论是**真独立**还是互相看过？
- [ ] 编排者有没有偷偷干活？
- [ ] 每个 agent 的上下文里有没有它用不到的东西？
- [ ] 失败会不会无限重试？
- [ ] 最终产物有没有地方**必须**写"我们内部有分歧"？

## 练习

1. 在本项目里找出至少三处专门防御"幻觉填空"的设计。
2. 失败模式 3（确认偏误串联）与失败模式 7（过度圆滑）都与"分歧"有关，
   它们的区别是什么？
3. 设计一个自动检查：如何用代码检测出"report.md 里的某个数字没有出现在任何一份分析产物里"？
