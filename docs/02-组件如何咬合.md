# 02 · 组件如何咬合

## 一、一句话区分六层

| 层 | 回答的问题 | 放什么 | 不放什么 |
|---|---|---|---|
| Agent | 我是谁 | 职责、输入输出边界 | 算法、代码 |
| Skill | 这类事怎么做 | 方法论、清单、模板 | 具体某次运行的数据 |
| Tool | 我怎么动手 | CLI 薄封装 | 业务逻辑、编排 |
| Contract | 我们传什么 | 字段结构与约束 | 业务含义的解释 |
| Memory | 上次学到什么 | 踩坑、决策、运行摘要 | 通用方法论 |
| Workspace | 这次发生了什么 | 中间产物与日志 | 需要长期保留的东西 |

## 二、最容易混的三组边界

### Skill vs Memory

- Skill：**通用**方法论 —— "判断板块强弱要看联动、带动性、容量、梯队、相对指数五项"
- Memory：**本项目**经验 —— "AKShare 的炸板池只能取最近 30 个交易日"

判断法：**换一个项目还成立吗？** 成立 → skill；不成立 → memory。

### Skill vs Tool

- Skill：需要**判断**的部分 → 给模型看
- Tool：需要**精确**的部分 → 让代码算

判断法：**同样的输入，要求每次输出完全一样吗？**

本项目的对照：

| 事情 | 归属 | 为什么 |
|---|---|---|
| 炸板率是多少 | Tool（`fetch_dataset`） | 必须每次一样，否则报告不可复现 |
| 这个炸板率说明情绪到哪一步 | Skill（`market-emotion-cycle`） | 需要结合梯队、晋级率综合判断 |
| 单笔风险是不是超 0.5% | Tool（`compute_risk`） | 算错小数点，风险判断就完全反了 |
| 超限了该砍还是该不加仓 | Skill（`risk-discipline`） | 取决于是存量还是新开仓 |

### Tool vs Script

- Tool：接口层，负责参数解析与 JSON 输入输出，**很薄**
- Script：实现层，负责真正的逻辑，**可单测**

看 `tools/fetch_dataset.py`：它只有 40 行，真正的取数在 `scripts/build_dataset.py`。
好处是 `tests/test_breadth.py` 可以直接测取数逻辑，不用去起一个 CLI 进程。

## 三、依赖方向（不许反向）

```
agents  ──调用──▶  tools  ──调用──▶  scripts  ──访问──▶  AKShare
   │
   ├──加载──▶  skills        （只读方法论）
   ├──读写──▶  workspace     （受 schemas 约束）
   └──读写──▶  memory        （跨 run 保留）
```

**反向依赖是设计事故：**

- ❌ `scripts/` 里写 prompt 或调用模型
- ❌ `scripts/fetch/news.py` 里给新闻打"利好/利空"标签（那是 news-analyst 的判断）
- ❌ `skills/` 里写死某次运行的数据
- ❌ agent 里手写 HTML（渲染是 `tools/render_report.py` 的事）

第二条特别值得说：取数层给新闻打标签会看起来"很方便"，
但那等于把判断藏进了一个没人会去 review 的地方，而且没法解释理由。

## 四、加一个新东西时，改哪几处

| 新增什么 | 需要同步改动的地方 |
|---|---|
| 一个 agent | `agents/*.md` → `schemas/*.json` → orchestrator 调度表 → `pipeline.yaml` → `AGENTS.md` 流程图 → 示例 run → 测试 |
| 一个 skill | `skills/<name>/SKILL.md` → 在引用它的 agent 的 `skills:` 里登记 |
| 一个 tool | `tools/<name>.py` → `tool_manifest.yaml` → agent 的 `tools:` 里登记 |
| 一个数据块 | `scripts/fetch/` → `build_dataset.py` → `dataset.schema.json` 的 enum → `contracts.BLOCK_NAMES` |
| 一个字段 | `schemas/*.json` → agent 定义的输出说明 → 示例 run → 跑 validate |

**漏改任何一处，系统都会以"不报错但结果不对"的方式失败。**

本项目有测试守着其中几处：
`test_every_agent_writes_a_schema_that_exists`、
`test_every_tool_in_manifest_exists`、
`test_block_names_match_schema`。
加新东西时先跑 `pytest tests/ -q`，能挡掉大部分漏改。

## 五、依赖门槛也是接口的一部分

本项目原本写着 `Python >= 3.10`。一个学生装完所有依赖，只卡在这一条上。

排查结论是：**代码里根本没用到 3.10 的任何特性**——
没有 `match` 语句，注解里的 `str | None` 也都有 `from __future__ import annotations` 兜着。
那条下限是拍脑袋定的，白白把人挡在门外。

于是做了三件事：

1. 下限降到 3.9，`doctor` 对 3.9 给"能跑，但建议升"的**黄色提示**而不是红色拦截
2. `doctor` 的修复建议改成**这台机器上最短的路径**——
   检测到在 venv 里就提醒"光装新 Python 没用，venv 必须重建"
3. 写 `tests/test_py_compat.py` 守住它：
   以后谁写了 `match` 或运行时联合类型，测试立刻红

> 教学要点：**每提高一个版本下限，就有一批人被挡在门外。**
> 提之前先问"我真的用到了那个版本的特性吗"，
> 然后写个测试把答案固定下来——否则半年后又会悄悄漂回去。
